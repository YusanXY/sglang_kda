# DeepSeek V4 增量 prefill 加速分析报告

## 1. 结论

在 SGLang commit `3db548f5e`、4 张 NVIDIA B200、TP=4、EP=4 上，使用
`one_batch_server.py` 完成了一组单样本端到端对照：

| 配置 | E2E latency | TTFT | 4096-token 增量吞吐 |
|---|---:|---:|---:|
| 原生 baseline | 0.3831 s | 0.3828 s | 10700 tok/s |
| KDA two-slot reference | 0.2650 s | 0.2647 s | 15474 tok/s |
| 变化 | -30.8% | -30.9% | +44.6% |

正式 measured request 在两份日志中都被确认是：

```text
#new-seq: 1, #new-token: 4096, #cached-token: 61440
```

因此，本轮比较的是最终 context 65536 下的 4096-token 增量 chunked
prefill，batch/request 数为 1，输出为 1 token。两轮均以退出码 0 完成。

该结果是性能路径验证，不包含 logits 或生成结果的数值一致性比较；并且每种配置
只有一个样本，不能把 1.45× 直接视为稳定收益。

### 3.1 Adapter 与 reference 映射

`reference_adapters/sglang_entry.py` 从以下只读目录导入正式实现：

```text
/home/gjy/data/agent4kernel/mega_mqa_logits/llm_flops/operators/references/
```

映射如下：

| KDA slot | reference 目录 | adapter 行为 |
|---|---|---|
| `deepseek_v4.indexer_fp8_quant` | `deepseek_v4_indexer_fp8_quant` | 必要时把 `weight` 转为 contiguous，再调用 reference `operator` |
| `deepseek_v4.paged_mqa_logits` | `deepseek_v4_fp8_paged_mqa_logits` | 去掉 SGLang 的 singleton 维并传入 KV、page table、schedule 和 offset |

这份配置没有直接路由
`deepseek_v4_chunked_mega_mqa_logits` 的 producer/history_hidden 完整 ABI。当前
SGLang KDA slot 边界仍是 `indexer_fp8_quant` 与 `paged_mqa_logits`；前者产生
量化 query，后者消费已经存在的物理 C4 KV cache。

配置中的 `root` 是绝对路径，因此只能在当前目录布局下直接复现。reference
目录本身没有可直接用于 SGLang 的 `sglang_entry.py`，部署依赖当前 runtime
adapter。KDA 不提供异常后的 native fallback。

## 4. 当前加速原因分析

### 4.1 能确认的执行差异

两个 reference 不是完全不同的数学算法：

- `deepseek_v4_indexer_fp8_quant` 最终调用 SGLang 的
  `fused_q_indexer_rope_hadamard_quant`；
- `deepseek_v4_fp8_paged_mqa_logits` 最终调用
  `deep_gemm.fp8_paged_mqa_logits`；
- baseline 在相同两个 SGLang 调用点也使用上述 native kernel family。

可从源码直接确认的主要差异是 adapter 边界归一化：

1. indexer adapter 对非 contiguous 的 `weight` 显式执行
   `weight.contiguous()`；
2. paged-MQA adapter 把 SGLang 的 query singleton 维归一化后，经
   `deepgemm_paged_mqa_logits_split` 重新构造 DeepGEMM 输入；
3. route 在启动期冻结，正式热路径只有一次 callable/None 分支，不读取 YAML。

其中第 1 点可能减少 fused indexer 对 strided weight 的低效访问，是当前最值得
优先验证的假设。第 2 点最终仍构造等价的 `[M, 1, H, D]` 输入，理论上不应单独
解释 30% 的整模型差异。KDA 路由自身的 Python 开销也不可能产生正向 30%
收益。

### 4.2 为什么暂时不能唯一归因

当前只有 baseline 和 two-slot profile 各一个样本，且两轮分别重启 server。
下列因素仍可能影响结果：

- B200 GPU clock、温度和前一轮负载状态；
- Torch extension、DeepGEMM JIT 和文件系统 cache 的先后顺序；
- server 启动和首次正式 shape 的运行时状态；
- 61440-token prefix warmup 对后续 kernel/cache 的预热程度；
- 客户端 TTFT 包含 HTTP、调度和首 token 返回，不是纯 kernel 时间。

两轮 prefix warmup 后段的 scheduler throughput 也存在明显差异，说明收益并不
只体现在最后一个 HTTP 请求。需要算子拆分和 profiler 才能区分 contiguous copy、
kernel 执行与运行顺序效应。

因此，当前合理结论是“two-slot reference profile 在这一单次端到端观测中快
1.45×”，而不是“某个新 MQA 算法已经确定贡献 1.45×”。

## 5. 下一步归因实验

建议建立四个 profile，并在相同顺序策略下各运行至少 5 次：

| Profile | `indexer_fp8_quant` | `paged_mqa_logits` | 目的 |
|---|---|---|---|
| native | off | off | 基线 |
| quant-only | reference | native | 测 contiguous/quant 边界 |
| mqa-only | native | reference | 测 paged-MQA adapter |
| two-slot | reference | reference | 测组合收益 |

每轮应：

1. 交替 profile 顺序，并确认 GPU memory 完全释放；
2. 保存 client JSONL、server log 和 GPU clock/power；
3. 报告 median、P10/P90 和 CV，而非只报最佳值；
4. 用 Torch/Nsight profiler 分别统计 fused indexer 与 paged MQA kernel；
5. 记录 adapter 中 `weight.is_contiguous()`、shape 和 stride；
6. 增加 correctness case，比较关键中间 tensor 或最终 logits；
7. 若目标是完整 `chunked_mega_mqa_logits` ABI，新增专用 KDA slot 或 adapter
   boundary，不能把当前 paged-MQA route 当成等价接入。

## 6. 本次运行中的非结果性异常

第一次尝试使用 `context_length=65537`，正式 65536-token prompt 被模型长度
保护拒绝；第二次立即重启时，一张 GPU 尚未释放约 37.6 GiB，触发 TP memory
balance 保护。两次失败均未进入结果比较。待 GPU 全部回到 0 MiB 后，使用
`context_length=69632` 的 baseline 与 reference 均成功完成。

两份成功日志都有非致命的 `cutlass.cute.experimental` package-walk warning，
没有 traceback、OOM 或 adapter fallback。
